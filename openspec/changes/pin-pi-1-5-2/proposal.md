## Why

`.version` pins Pi 0.80.8 (2026-07-16), about four months and one major
version behind. On 2026-11-18 the six repositories agreed to pin the newest
stable release that was at least 72 hours old on that date. For Pi this is
**1.5.2** (2026-11-10). For OpenSpec it is **2.0.0** (2026-11-11).

The jump covers 0.81–0.87 and 1.0–1.5. Pi now has built-in MCP support
(`@earendil-works/pi-mcp`), codemode (`@earendil-works/pi-codemode`) and a
project trust gate for project-local resources. The endpoint and control
measurements of 0.80.8 therefore no longer describe the shipped agent.

## What Changes

- **Pins:**
  - `.version`: `0.80.8` → `1.5.2`.
  - `Containerfile`: `OPENSPEC_VERSION` `1.16.0` → `2.0.0`. The base digest is
    unchanged. Pi 1.5.2 still declares `node >=22.19.0`.
- **Policy:** `agent/policies/default.json` sets `tested.cli` to 1.5.2 with the
  new measurement dates. The policy gets a new revision only if the hosts change.
- **Tests that name the version:**
  - `tests/test_image_pins.py`;
  - `tests/test_network_runtime.py`;
  - `tests/test_runtime.py` (OpenSpec assertion);
  - any other test that asserts `0.80.8` or `1.16.0`.
- **Tracked OpenSpec skills:** `.agents/skills/openspec-*` are regenerated with
  OpenSpec 2.0.0. They were generated by 1.16.0, and 2.0 owns the
  `.agents/skills/` layout.
- **Documentation:**
  - version-specific statements in `README.md`, `docs/setup.md`,
    `docs/network-contract.md` and the agent help text in `agent/launcher.sh`,
    for example the claims about the tool-approval layer and `--approve`;
  - a dated entry in `docs/validation.md`;
  - a `CHANGELOG.md` entry.
- **Full remeasurement of 1.5.2, without credentials:**
  - static endpoint inventory;
  - logging-proxy runs for the four profiles;
  - the controls `PI_OFFLINE`, `PI_SKIP_VERSION_CHECK` and `PI_TELEMETRY`;
  - MCP and codemode behavior under the guard;
  - project trust behavior in the container.
- **BREAKING (upstream):**
  - Pi 1.x renamed the Azure provider and changed extension APIs.
  - Project `.agents/skills` and `.pi/*` resources load only after project trust.
  - The wrapper does not use Azure. User extensions in `~/.pi` may need
    updates. The README notes both.

No shared launcher file changes and no new reference tag.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None expected. The `shared-launcher` scenario that uses `.version` = `0.80.8`
is an example and stays true. If the measurement finds a required host change,
or a behavior change that the specs describe (for example, Pi now asking for
tool approval), implementation pauses. The matching delta (`network-egress`,
`container-launcher`) is then added after the user agrees. Until then the
change sets `skip_specs: true`.

## Impact

- **Files:**
  - `.version`, `Containerfile`, `agent/policies/default.json` and
    `agent/launcher.sh` (help text only, if needed);
  - the tests listed above and `.agents/skills/openspec-*`;
  - `README.md`, `docs/setup.md`, `docs/network-contract.md`,
    `docs/validation.md` and `CHANGELOG.md`.
- **Image identity:** the image changes. Because `.version` is a hashed build
  input, the next launch asks for `--container-build`. The operator reruns
  `--container-setup` on the three hosts.
- **User state:** `~/.pi` and `~/.agents` are kept. Pi 1.x reads them and
  stores trust decisions in `~/.pi/agent/trust.json`.
- **Deferred:** real-key checks stay with the operator.
